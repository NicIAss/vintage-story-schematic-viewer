# Upgrading and rollback

This guide is for operators updating an existing wiki, schematic database, or
standalone deployment. Pin exact renderer and asset versions in production;
test them together before changing a public URL.

## Record the running deployment

Before changing anything, record:

- the renderer release tag or Git commit (`window.vsSchematicViewer.version`
  reports the public API version);
- the deployed asset-registry path and the Vintage Story asset version used to
  build it;
- the current iframe query parameters or same-origin `setOptions()` values;
- the schematic URLs used for smoke tests; and
- the location of the previous application bundle and registry for rollback.

Do not overwrite the only working copy. Use immutable directories such as
`viewer/0.4.2/` and `vs-assets/1.22.5/<registry-hash>/`, then change a small
channel or configuration pointer after verification.

## Fetch and verify a renderer release

On Windows PowerShell or Ubuntu/Bash:

```text
git fetch --tags origin
git checkout v0.4.2
pnpm install --frozen-lockfile
pnpm test
pnpm typecheck
pnpm build
```

The production viewer is written to `apps/desktop/dist/`. Deploy it to a new
versioned directory first. Do not build production directly from an unpinned
`main` branch.

## Decide whether to rebuild the asset registry

Renderer-only UI, camera, and performance fixes normally require only a new
application bundle. Rebuild the registry when any of the following is true:

- the release notes mention compiler, registry, shape, texture, tint, or block
  metadata changes;
- the website is adopting assets from a new Vintage Story release; or
- the existing registry was generated by an unknown compiler revision.

Version 0.2.0 keeps registry format v2 but adds compatible metadata for logical
texture dimensions, element render passes, and fruit trees. An older format-v2
registry still loads, but the tall-door UV, transparent-window, and dynamic
fruit-tree improvements are unavailable. A rebuild is therefore required for
the full 0.2.0 rendering result. PNG textures do not need conversion, and
schematic JSON files need no migration.

Compile from a legally obtained game asset directory, never from files stored
in this repository:

```bash
pnpm assets:compile -- \
  --assets "/path/to/Vintagestory/assets" \
  --output "./deploy/vs-assets/1.22.5/asset-registry.json" \
  --texture-base-url "https://cdn.example.org/vs-assets/1.22.5" \
  --portable
```

PowerShell accepts the same arguments on one line. Publish the registry beside
the matching `game/textures`, `survival/textures`, and `creative/textures`
hierarchy. Keep the previous registry available until the deployment has been
verified. See [Asset pipeline](asset-pipeline.md) for the full layout and legal
boundary.

## Stage and smoke-test

Point a staging viewer at the new application and registry. Test at least one
representative schematic for each changed rendering path. The baseline checks
from 0.2.0 remain useful:

- a tall ruined door with its wood and moss textures correctly scaled;
- a window with an opaque frame and transparent glass;
- short support beams for position and direction;
- fruit-tree branches, foliage, growth direction, and tint;
- unresolved blocks hidden by default but still counted in diagnostics; and
- orbit controls on desktop and touch controls on mobile. Fly mode is
  intentionally unavailable on touch-only mobile devices.

Also exercise the exact iframe preset used by each consuming website and one
GIF export. Version 0.2.0 adds `unresolved=on|off`, the same-origin
`unresolvedBlocks` option, and the GIF `includeUnresolvedBlocks` option. Their
defaults hide unresolved colored placeholders.

When all checks pass, update the production pointer or embed URL. Purge CDN
caches only for mutable aliases; immutable versioned or content-hashed paths
should not be purged.

## Roll back

If a regression appears:

1. restore the previous viewer directory or channel pointer;
2. restore the exact registry URL used with that viewer;
3. restore the previous iframe/API option preset; and
4. verify one known schematic and inspect browser cache/CDN headers.

Rollback does not modify schematic files. Keep old application bundles and
registries until the new release has been stable for the site's normal review
period.

## Checklist for automated maintenance agents

An AI model or deployment automation updating a running service should:

1. read `README.md`, `CHANGELOG.md`, this guide, `docs/asset-pipeline.md`, and
   `docs/website-integration.md` at the target tag;
2. report the old and new renderer tags, game-asset version, registry format,
   and whether a registry rebuild is required;
3. preserve public URL parameter and same-origin API behavior unless the
   release notes explicitly describe a migration;
4. never commit or redistribute Vintage Story assets, generated registries,
   official source, DLLs, schematics, or `_local/` inputs;
5. avoid regenerating a registry when the legally obtained asset input is not
   available—deploy only compatible renderer changes or stop and report the
   missing prerequisite;
6. run `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm typecheck`, and
   `pnpm build` before deployment;
7. deploy to a staged immutable path, perform the representative smoke tests,
   then switch the production pointer; and
8. retain and document a tested rollback target.

Do not infer Vintage Story compatibility from the renderer version. Renderer
releases and game-asset manifests are intentionally versioned independently.

## 0.2.0 to 0.3.0

Version 0.3.0 changes only the deployable viewer application. Keep the existing
0.2.0-compatible format-v2 registry and textures; no registry rebuild or
schematic migration is needed.

Replace the versioned application bundle, then update website iframe URLs to
use `mode=embed`. Use `controls` as an explicit allowlist when visitors should
not change fixed display settings. For example:

```text
?mode=embed&controls=recenter,top&grid=off&bounds=off&meta=off&unresolved=off
```

Smoke-test that local file buttons never appear during the predefined
schematic's initial load, file drag/drop is ignored, allowed controls remain
usable, and omitted controls do not occupy toolbar space. The old standalone
behavior remains the default for URLs without `mode=embed`.

## 0.3.0 to 0.4.0

Version 0.4.0 changes only the deployable viewer application. Keep the existing
format-v2 registry and texture hierarchy; no registry rebuild or schematic
migration is needed.

The side information panel now starts hidden. Add `info` to the `controls`
allowlist when visitors should be able to open it, and use `inspector=on` only
for pages that should start with the panel expanded. On narrow screens the
expanded panel overlays the viewport. Smoke-test both toggle states and any
embed that intentionally omits the `info` action.

## 0.4.0 to 0.4.1

Version 0.4.1 changes only the renderer bundle. Keep the existing format-v2
registry and texture hierarchy; no registry rebuild or schematic migration is
needed.

Surface decors now follow the resolved host geometry rather than occupying a
full block-cell face. Stage at least one schematic containing dust or moss on
partial JSON shapes and one containing rotated clutter, such as a wagon wheel.
Confirm that the overlay follows the visible surface and no longer floats at
the nominal one-block outline. Existing iframe controls and same-origin APIs
are unchanged.

## 0.4.1 to 0.4.2

Version 0.4.2 adds loading feedback to the viewer and an optional progress
callback to renderer-core. Keep the existing format-v2 registry and texture
hierarchy; no registry rebuild or schematic migration is needed.

Smoke-test one small schematic and one large schematic through the same loading
path used by the website. The loading panel should announce download/read,
parsing, registry, texture, geometry, and finalization phases, reach 100%, then
fade away. Also verify that a failed schematic removes the loading panel and
leaves the existing error state readable. Existing iframe query parameters and
same-origin loading methods are unchanged.
